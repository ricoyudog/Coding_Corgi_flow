# CorgiSpec 4.0.0-rc2

CorgiSpec 4.0.0-rc2 fixes the RFC-first Propose retry defect found in rc1. A tracked Change that already persisted its single Issue can now finish `propose --finalize` without depending on tracker marker-search visibility and without creating a second Issue.

## Fixed

- Propose now reconciles persisted Issue authority in this order: RFC delivery binding, Change `corgi/source.yaml`, then Propose transaction intent.
- When any legal retry state already owns an Issue, Propose reads that exact Issue and verifies its id, original URL, and Corgi marker. Marker search and Issue creation are reserved for the first attempt with no persisted Issue.
- Conflicting persisted Issue references fail before any tracker call and report both raw identities. Original Issue URLs remain an exact, digest-bearing contract.
- Retries from `tracker_sync_pending` and repeated successful finalization remain idempotent.
- The prerelease workflow now recognizes the v4 `4.0.0-rcN` sequence, publishes only to npm `next`, and runs the supported OpenSpec prerequisite.

## Upgrade

```bash
npm install -g corgispec@4.0.0-rc2
corgispec --version
```

For a managed installation, rerun the applicable CorgiSpec bootstrap update for each selected platform and scope. Projects still on v3 must first finish, archive, or withdraw active work and follow the explicit v4 migration flow documented in `INSTALL.md`.

## Retry the affected delivery

After upgrading, rerun the original command unchanged:

```bash
corgispec propose "<change>" \
  --from "<RFC-ID>/<SLICE-ID>" \
  --finalize \
  --json
```

Do not edit `delivery.yaml` manually. The CLI reuses the Issue recorded by the existing transaction/source state and completes the owned CAS transition.
